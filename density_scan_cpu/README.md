# MACELES-LES 密度扫描机制（CPU / 直接力场模式）

本目录收录"一台 CPU 集群上跑 6 分子 × 10 档密度共 60 个状态"这一整套机制：
参数化、分片、作业模板、驱动脚本、后处理，以及踩过的坑。

---

## 1. 状态一览

| 项 | 值 |
|---|---|
| 分子 | H2O、NH3、CH4、C2H4、C2H6、CO2 |
| 密度档 | ρ\* = linspace(0.02, 0.67, 10) |
| 状态数 | 6 × 10 = **60** |
| 并发作业 | 24 个（主扫描）+ 6 个（ρ\*=0.02 单点，后期追加）= 30 |
| 每档时长 | 100 ps 平衡 + 1 ns 生产 |
| 时间步 | 0.5 fs |

## 2. 密度参数化

采用完整 LJ 的参考临界量 `T*c = 1.312`、`ρ*c = 0.316`：

```
σ³   = 0.316 / ρc          (ρc 为真实流体临界密度, mol/Å³)
ρ    = ρ* / σ³             (mol/Å³)
ε/kB = Tc / 1.312
T    = 1.5244 × Tc         (即 2Tc/1.312, 约 2 倍临界温度)
```

## 3. 分片结构

每个分子 10 档拆 4 个 shard，**3 + 3 + 2 + 2**，每个 SLURM 作业按密度**从高到低串行**跑一个 shard：

| shard | ρ\* 档 | 每作业状态数 |
|---|---|---|
| `_1` | 0.6700 / 0.5978 / 0.5256 | 3 |
| `_2` | 0.4533 / 0.3811 / 0.3089 | 3 |
| `_3` | 0.2367 / 0.1644 | 2 |
| `_4` | 0.0922 | 1（原为 0.0922+0.02，0.02 拆出单跑） |
| `_lo` | 0.0200 | 1（追加的 6 个单点作业） |

CO2 用的是 `shard_5..8`（同样的 3+3+2+2）。

## 4. 单个作业的 MD 流程（见 `templates/in.les_md.template`）

```
velocity create 300
fix nvt temp 300  <T>  0.1  ; run 40000      # 升温 ramp (20 ps)
fix nvt temp <T>   <T> 0.1  ; run 160000     # 平衡   (80 ps)
reset_timestep 0
write_restart restart_100ps                  # 平衡结束的 restart
dump ... every 1000                           # 生产段轨迹
run 2000000                                  # 生产   (1 ns)
write_restart restart_1ns                    # 生产结束的 restart
```

合计 220 万步/状态 = 1.1 ns。

### 力场与并行（CPU 直接模式）

```
pair_style symmetrix/mace/float32/kk streamed_edges direct profile capacity \
           jit_host_artifact <factorized_host_plugin.so>
pair_coeff * * <maceles_off_chno.json> C H N O
neighbor 2.0 bin
```

- `mpirun --allow-run-as-root --oversubscribe -np <N> lmp -k on t 1 -in in.les_md`
- JIT 模式下 `streamed_edges` **只能是 `direct`**（写成 materialized 会直接报错）
- 核数：H2O/NH3/CH4/CO2 = 32，C2H4/C2H6 = 48

## 5. 实测速率（hours per ns，含 1.1 ns 全程）

以 CO2/32 核为基准，其它分子按 `N原子/2001 ÷ √(核数/32)` 缩放：

| ρ\* | 0.67 | 0.5978 | 0.5256 | 0.4533 | 0.3811 | 0.3089 | 0.2367 | 0.1644 | 0.0922 | 0.02 |
|---|---|---|---|---|---|---|---|---|---|---|
| H2O/NH3/CO2 | 37 | 38 | 39 | 40 | 42 | 45 | 49 | 62 | 88 | 220+ |
| CH4 | 47 | 48 | 49 | 50 | 53 | 56 | 62 | 77 | 110 | 280+ |
| C2H4 | 46 | 47 | 48 | 49 | 52 | 55 | 60 | 75 | 107 | 270+ |
| C2H6 | 61 | 62 | 64 | 65 | 69 | 74 | 80 | 101 | 143 | 364+ |

**低密度实际比上表更慢**：ρ\*=0.02 实测每步 0.24~1.5 s（见第 8 节）。

## 6. 后处理

每个 shard 的 sbatch 在 MD 之后自动跑 `postprocess_shard.py`：

```
les_batch.py --no-analyze --no-compress-traj   # 只跑 MD，保留轨迹
postprocess_shard.py --manifest <shard> --traj-root scan/traj --post-root scan/post
```

- 后处理**按 shard 触发**（该 shard 全部状态跑完才做），不是每个状态跑完就做
- 产物：`post/<sim_id>/{f1,f2}` + `les_c1c2.json` 标记（有标记就跳过，可重复运行）

## 7. 运维要点 / 踩过的坑

1. **manifest 只在作业启动时读一次**  
   作业跑起来后再改 `manifest.csv` 对它**无效**（已读进内存）。想中途放弃某个状态，
   唯一办法是写 `traj/<sim_id>/meta.json`，内容 `{"status": "skipped_not_run"}` ——
   `run_row()` 每行都现查这个文件，看到就 skip。

2. **`--resume` 不续跑，只跳过**  
   已完成（有 `meta.json`）的 sim_id 跳过；未完成的状态会被改名成
   `*.partial.<时间戳>` 然后**从头重跑**。所以被配额/超时杀掉的作业，那一档的进度全丢。

3. **没有中途 restart**  
   当前模板只写 `restart_100ps` / `restart_1ns`，生产段中途被杀无法续跑。
   建议加：
   ```
   restart 20000
   write_restart restart.*
   ```
   这样任何中断最多丢 100 ps。

4. **磁盘配额会被日志吃光（最大的坑）**  
   `log.les_md` 里 99.9%（约 231 万行）是 Symmetrix 每次重建图时每个 rank 打的
   `graph capacity:` 诊断串，60 个状态能到 **91 GB**，而真正的 `traj.dump` 只有 12 GB。
   曾因此撞 `Disk quota exceeded` 被杀掉 3 个作业。
   ```
   已完成状态: gzip traj.dump；删日志
   在跑状态  : 超过 200 MB 就截断，只留最后 2 MB
   ```
   压完 108 GB → 7 GB。

5. **低密度不是"图重建"的锅**  
   计时分解显示 `Neigh` 0.0%、`Comm` ≤2%、`Pair` 98%+；
   `compute symmetrix/timing` 进一步显示隐藏态通信只占 0.31%，
   罪魁是 `SxNonComm`（内核计算）：ρ\*=0.02 每原子 336 µs vs ρ\*=0.2367 的 36 µs（9.3 倍），
   而边数只少 2.5 倍。换 `profile speed`、`neighbor 4.0`、减核数都**无效**；
   `compute symmetrix/timing` 是定位这类问题的正确工具。

6. **`rho_c` 必须用精确 σ³ 反推**，别用文献里四舍五入的值（见第 2 节）。
